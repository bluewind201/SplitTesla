## 공유 음성

`Speaker`는 독립 엔진 대신 applicationContext 기반 프로세스 공유 엔진의 소유권 lease다. 카메라·내비·비서·설정 미리듣기가 동일한 재생 큐를 사용한다. 설정 화면의 별도 TTS는 음성 목록 조회만 하고 재생하지 않는다. 각 lease는 고유 ID를 가지며 stop/shutdown은 그 소유자의 대기·현재 발화만 취소한다. 다른 소유자가 재생 중이면 건드리지 않는다. 마지막 lease 해제에서만 엔진 shutdown하며 이후 생성은 새 엔진을 초기화한다. 카메라 서비스의 로딩 중 중복 start도 막았다.

순수 Kotlin `SpeechQueue` 정책(모두 자체 설계):

| 발화 | 우선순위 | 대기 만료 |
|---|---:|---:|
| 카메라 최종 | 100 | 3초 |
| 턴 및 일반 내비 | 70 | 생성 시점부터 5초 |
| 카메라 예고/구간 지점 | 60 | 6초 |
| 자동 경로 이탈 재탐색 | 30 | 생성 시점부터 5초 |
| 비서 | 10 | 8초 |
| 설정 미리듣기 | 10 | 3초 |

동일 우선순위는 FIFO, 대기 최대32개이며 혼잡 시 더 낮은 우선순위의 대기 발화만 밀어낸다. 초기화 전에도 여러 요청을 보존하며 재생 직전 만료를 검사한다. 단조시각(elapsedRealtime)을 사용한다. 동일 key의 대기/재생 중복 및 시작 후8초 중복을 억제한다. 카메라 key는 ID·종류·예고거리 구간을 포함하며 같은 카메라의 새 단계는 대기 중인 이전 단계를 대체한다. 필수 안내(60 이상)는 재생 중인 비서/재탐색 같은 낮은 우선순위 발화를 선점할 수 있으나 재생 중인 필수 안내끼리는 자르지 않는다. 기존 interrupt 인자는 타 소유자를 자르는 QUEUE_FLUSH로 해석하지 않는다.

실제 TTS에는 항상 한 문장만 QUEUE_ADD로 넘긴다. utterance ID를 확인하여 늦게 도착한 stop/done/error 콜백이 다음 문장을 완료시키지 못하게 했다. 재생 전 오디오 포커스 요청 성공을 확인하고 실패 시 그 문장은 건너뛴다. 포커스 상실 시 현재 문장을 취소하며 오래된 거리 문장을 재생하지 않는다. 완료·오류·취소·포커스 상실·마지막 해제 시 포커스를 반환한다. 엔진 콜백 누락은30초 watchdog으로 해제한다. 엔진 실패·한국어 데이터 미설치 시 발화하지 않는다.

기존 voice prefs의 name/rate를 유지하고 같은 prefs에 muted=false 기본값을 추가했다. 전체 음소거는 대기/현재 발화를 취소하며 서비스 재시작에도 유지된다. 내비의 기존 voice 설정도 발화 생성·서비스 전달·공유 큐 재생 직전 확인한다. 설정 미리듣기의 음성/속도 override는 저장된 선택을 바꾸지 않는다. 내비의 전달 채널에도 생성 시점 만료를 담아 서비스 재시작 후 오래된 턴을 읽지 않는다.

## 선택형 제한속도 프리셋

기존 주행속도×12초(200–600m) 예고와 최종100m가 기본이다. 기존 설정을 마이그레이션하거나 기본값을 바꾸지 않았다. Compose 카메라 설정에 “제한속도 기준 미리 알림” 토글을 추가했다. 새 boolean camera_limit_preset만 저장하며 실행 중 서비스도 다음 실제 fix에서 읽는다.

원본 분석의 §1.2 및 §4는 제한속도80이상1000/500m,50이상600/300m,50미만300m를 관찰값(높은 신뢰)으로 기록한다. ±100/75/50m 창도 관찰되어 있으나 이 앱에는 그대로 이식하지 않았다. 본 앱의 실제 승인 fix·방향·접근 확인을 그대로 유지하고, 해당 임계값 이하의 첫 접근에서 현재 실제 거리를 읽는 catch-up 방식을 자체 설계했다. 관찰된 후면 유지 거리, 경고음 간격, 과속 버퍼, 독점 경로/구간 데이터는 추가하지 않았다. 미확인 수치를 네이버 동작으로 주장하지 않는다.

샘플이1000m와500m를 한꺼번에 건너뛰면 과거 두 문장을 몰아 읽지 않고 현재 거리로 예고 한 번만 한다. 이미 건너뛴 단계는 소모한다. 최초 근거리 감지에서도 현재 예고 한 번과 실제100m 이하 최종 한 번만 내며, 최초100m 이하는 최종만 낸다. 최종 이후 예고는 없다. 예고한 카메라에 대해 프리셋을 변경하면 추가 예고를 재생하지 않고 최종100m를 유지한다. 이 설정전환 정책은 자체 설계다. 발화는 기존 실제 거리 반올림 규칙을 사용하고 고정100m 문구로 회귀시키지 않았다. 좌표 오차로 잘못된 거리를 보고할 가능성은 공공 좌표/위치 증거 자체의 한계로 남는다.

## L2 표시

QA가 지적한 “GPS 신호 약함: 차량 속도로 위치를 추정 중”은 속도 없음/추정 만료에도 남을 수 있어 제거했다. 주안내 TurnCard(컴팩트 포함), TurnBanner, 내비 알림은 순수 상태 정책을 사용한다.

- 실제 양호 진행: 정상 턴/거리.
- 아직 진행 없음: 위치 확인 중.
- 이번 주기 유효 차량속도·시간으로 허용된 추정 적분: 위치 추정 중 · 턴/거리 예상.
- 그 외 위치 불확실/추정 만료: 안내 일시 보류 · 턴/거리 확인 필요.

불확실한 턴 거리와 확정처럼 보이는 문구·연속턴은 주안내 영역에서 숨기고 확인 후 안내 문구를 보인다. 카메라 설정의 위치 상태는 “카메라: 위치 수신 중 (길안내 상태와 별도)” 또는 경고 보류로 명시한다. 안내의30m 정확도 계약과 카메라60m 계약은 바꾸지 않았으며 전체GPS가 정상이라는 뜻으로 합치지 않았다. 지도와 보조 남은거리·배터리 수치는 마지막/추정 진행에 근거할 수 있으며 주안내 상태 문구로 불확실성을 드러낸다. 실기기 폭·폰트 크기에서 배너 가독성 확인이 필요하다.

## Q1: 마지막 단계 안내의 재생 기회 복구 (추가 PM 정책)

이 절은 위 P2 수정 절의 “폐기된 같은 단계는 재시도하지 않음” 한계를 대체한다. 낡은 문장을 자동 재큐잉하는 대신 현재 턴이 아직 앞이고 위치/단계 신뢰가 유효할 때 **현재 정보로 새 시도**를 만든다.

- GuidanceAnnouncer.nextForPlayback는 PlaybackNotice(attempt)를 만들고, playback(notice, SpeechOutcome)으로 TTS 수락·실제 시작·완료·폐기·중단을 구분한다. 기존 next API는 생성 즉시 소비하는 레거시 호출용으로 유지한다. 실제 NaviHub는 nextForPlayback만 사용한다.
- TTS가 수락했거나 재생 중인 동일 단계는 반복하지 않는다. 실제 완료된 단계는 다시 생성하지 않는다. 마지막 단계가 중단/폐기되면 다음 양호 진행에서 현재 턴이 여전히 앞일 때만 새 attempt를 생성한다. 경로 변경·이미 지난 턴·offRoute·위치 불확실에서는 재발화하지 않는다.
- 대기 중인 시도가 오래되거나 진행이 바뀌면 최신 fix의 텍스트·컨텍스트로 새 시도를 만들어 이전 대기를 대체한다. 대기 갱신은 재생 중 반복과 다르다. 이로써36km/h 이상에서10m 이동 때문에 대기안내를 계속 폐기하기만 하는 경우에도 최신 안내가 재생될 기회를 유지한다. 재생 직전1.5초·10m 검증은 그대로다.
- 실제 NaviService 전달 어댑터는 상태 피드백도 Speaker까지 전달한다. 큐 만료/유효성 거절/그룹 대체/소유자 취소, TTS 포커스 거절/오류/완료/선점이 피드백을 만든다. TTS.onStart는 별도 STARTED, speak 성공은 ACCEPTED이며 두 상태 모두 중복 생성 방지에 쓰고 실제 완료를 따로 기록한다. 오래된 attempt의 늦은 피드백은 새 attempt를 변경하지 못한다.
- 재생 상태는 동기화된 순수 announcer에 즉시 전달하여 다음 fix가 엔진 수락 피드백을 앞질러 같은 재생을 중복 생성하지 못하게 했다. 경로 버전은 UI 초기화와 무관한 프로세스 단조 증가값이다.

추가 순수 TurnPlaybackTest 6개는 중단 후 현재 마지막 턴 복구·완료 후 반복 금지,60km/h 대기 최신화·오래된 피드백 무시,지난 턴/불확실/offRoute 재생 금지,빠른 fix 중복/경로 초기화 후 늦은 콜백을 검사한다. 실제 서비스 전달 어댑터를 사용하는 개발 하네스에도 최종 경고가 마지막 턴을 자른 뒤 현재 정보의 새 턴이 한 번 재생되고 완료 뒤 반복되지 않는 시나리오를 추가했다.

중간 결과(214/164/50 일반 통과, 기존 QA71개중70통과/R2실패, 구정책 하네스24개중23통과)는 Q1 이전 증거로 보존한다. QA 소유자가 구정책 단언을 v1 보존 후 v2로 갱신한 최신 파일을 최종 스냅샷에 복사했다. 개발자는 QA 소유 파일을 수정하지 않았다. QA 문서는 작성 중 외부 소유자 갱신으로 최초 문서 체크섬과 달라졌으며, 개발 수정으로 해석하지 않는다.

Q1의 대기 만료 보완은 마지막 단계 외에도 **실제로 폐기된 예고 단계**의 기회를 보존한다. 현재 단계가 아직 같으면 그때의 실제 거리로 새 예고를 만들고, 이미 다른 단계/턴이면 과거 문장을 재생하지 않는다. 대기/진행 중인 갱신 요청과 실제 재생 여부는 별도 관리한다. 채널 밀어내기·음소거·이미 닫힌 lease·큐 거절도 DROPPED 피드백을 보낸다. 기존 legacy next만 호출하고 실제 재생 결과를 통지하지 않는 테스트는 이 새 실제 호출 경로를 대신하지 못한다.

실제 시작 예약(claimStart)은 현재 attempt를 원자적으로 예약한다. 서비스 전달 어댑터가 컨텍스트 검사 뒤 이를 호출하므로 위치 fix 갱신이 TTS 수락 피드백을 앞질러 재생 중인 시도를 대체하는 경쟁을 막는다. 예약은 실제 ACCEPTED/STARTED/COMPLETED와 구분하며, 포커스 거절/검증 실패/취소 피드백에서 해제된다. 이 경쟁에 대한 순수 테스트도 포함했다.

### O1 영향과 타이머 판단

O1 `SpeakerOutcomeWiringTest.obs_expiryIsReportedWithoutWaitingForTheNextQueueActivity()`는 실패 그대로 남겼다. 현재 큐는 새 요청/재생 선택/현재 발화 종료 같은 **다음 큐 활동 때** 만료한 대기 요청에 DROPPED를 보낸다. 독립 만료 타이머가 없어 긴 발화 동안 아무 활동이 없으면 콜백이 늦는다. 단언을 바꾸거나 관찰을 통과로 세지 않았다. 별도 `expiringWhileWaitingReportsDropped`는 통과해 다음 활동 시 종료 결과가 전달됨을 확인했다.

QA의36·60·100km/h 반복 대기 폐기(S2), 중단 뒤 복구(S1), 위치 회복(S6), 유효 추정 복구(S9)가 모두 통과했다. 따라서 관찰된 지연이 **현재 복구 기회를 잃게 하지는 않았다**. 새 위치/속도 증거도 없는 동안에는 안전하게 현재성을 검증할 수 없어 재발화하지 않으며, 재획득 후 새 시도가 가능하다. 엔진 준비 실패 후 추가 활동도 없으면 종료 통지가 오래 남을 수 있다.
